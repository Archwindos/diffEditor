# DiffEditor

Use this workflow automatically for authorized creation and editing of material intended for the user to read, such as their papers, knowledge explanations, study notes, and discussion records. Reports and documentation qualify when they are reading material for the user. Adding text, proofreading, formatting, and restructuring count as edits. Decide by the material's intended use, not its extension, repository location, or edit size. Also use it when the user explicitly requests DiffEditor for another text review. Before writing, establish which files and claims the user authorized changing. Propose out-of-scope issues in chat without changing them. Preserve existing todo items and their states.

## Scope and execution boundary

- **Default exclusions:** Code, configuration, agent instruction files, and the agent's internal execution records (task checklists, progress logs, execution plans, and intermediate working notes) do not require DiffEditor unless the user explicitly requests review of them. Read-only analysis and ordinary chat replies also do not require it. A Markdown progress log used only to track the agent's work is not the user's knowledge note; a document prepared for the user to read is not exempt merely because it is named a log or checklist.
- **Tools do not change the scope:** For material requiring review, direct edits, patches, Python/PowerShell/shell scripts, batch jobs, other skills, delegated agents, and external tools obey the same boundary. Write and iterate in a separate temporary draft, then submit the accumulated result at the approval point described below. A script must not write the review-gated original. Pass this boundary explicitly to delegated agents and check their results. Available write access is not permission to bypass review.
- A one-time user instruction to skip diff and write directly applies only to the specified files and changes in that authorized round. Do not carry it into later revisions, other files, or another task. Ordinary chat approval such as "可以", "保存吧", or "继续" does not waive review. Never rewrite the user's saved result after receiving a receipt.
- DiffEditor handles plain text, including `.tex`, `.md`, `.bib`, `.txt`, and textual HTML. For unsupported formats or document services, explain the limitation and obtain the user's choice of a reviewable route before modifying the formal document. Do not treat lack of support as permission for a direct write or pretend a text receipt proves that a different document was saved.

## Choose the path per file

Apply these paths only to material within the review scope above; editing excluded code or internal progress records does not become review-gated after its first write.

- **First draft of a new document:** When the user authorizes creating a document, write its first content directly without a diff review or `baseline` / `submit` / `wait`, unless the user explicitly requests review of that first draft. Prefer creating the file once with its complete first draft using exclusive creation (`open(path, "xb")` in Python; `FileMode.CreateNew` in .NET). If you already created an empty placeholder in this task, verify that it is that same file and still empty before filling it. Read back the result before reporting creation complete; no DiffEditor receipt is needed for this path.
- **Revisions:** Once the first draft has been written to the formal document, subsequent changes require the review workflow below, even within the same task. This does not make each internal edit to a temporary working draft a separate round. Existing files, including empty files not created by you in this task, also use review. Never clear, delete, or recreate an existing document to qualify as a first draft; an existing pending proposal must remain in its review workflow.

For tasks mixing new documents and revisions, choose independently for each file and report direct creations separately from review save receipts.

## Review workflow

The approval unit is the accumulated result for one file within the current authorized task, not each model edit or script write. Follow the user's rule:

> 临时工作稿可以在授权范围内多次修改。中间修改不得逐次送审；只有到达需要人类批准的节点，才提交本轮累计的最终结果，并等待保存回执。

1. **Fix the baseline and create an independent working draft.** Run `baseline` for each target requiring review (including a new file when its first draft explicitly requires review) before generating candidate text. Read the returned text, encoding, existence flag, hash, and baseline ID. Preserve the JSON receipt using exclusive creation in a unique workflow directory under `%LOCALAPPDATA%\DiffEditor\inbox`, or `DIFFEDITOR_DATA_DIR\inbox` when configured. Create a distinct temporary text file there, such as `proposed.md` or `proposed.tex`, initialized from the captured baseline when editing existing text. It must be an independent file, not a link or alias to the original. Keep the baseline immutable throughout the round; do not create or overwrite the review-gated original or place temporary candidates in its directory. If an earlier review blocks this target, inspect or wait on its existing review IDs instead of starting another round.
2. **Complete the authorized work in that temporary draft.** The model and scripts may repeatedly edit, inspect, test, and correct the working draft within the authorized scope. Direct script output (and input for in-place transformations) to that path. Read back and check the complete result, preserving newlines. Do not open review windows, `submit`, or `wait` after intermediate writes. Reach the end of the authorized work and self-checks, or the next point requiring a human decision, before submitting the round's accumulated final result.
3. **Submit once at the approval point, then freeze the proposal.** Serialize the original file's baseline ID and the complete temporary draft text into UTF-8 `candidate.json` in the same workflow directory. Include `source` with the agent name, the actual initiating `CODEX_THREAD_ID` when available, and `threadTitle` only when the real conversation title is known. When the Codex app exposes thread tools, match the actual thread ID to its displayed title; if unavailable, retain the ID and omit the title. Never read internal app databases to guess it; do not substitute an invented task summary or claim to know a legacy review's origin. Keep this metadata in the frozen payload. The CLI can fill Codex and its environment thread ID when omitted. The CLI takes baseline IDs and text, not a pair of file-path arguments: the original baseline appears as the original, the temporary file's contents as the new draft, and the original path remains the save target. Do not baseline the temporary file. Use a real JSON serializer, then run `submit --file <absolute-candidate.json>` or feed the JSON bytes through `submit --stdin`; never interpolate document text into a shell command, flag, or here-string. Assign one unique `requestId` to this accumulated proposal and retain it with the exact payload for idempotent retries. After submission, freeze the AI's submitted draft and payload. Do not change the submitted text, allocate a new request ID, refresh the baseline, create another comparison, or use a path alias around an unresolved review; use the explicit withdrawal route below when retracting the proposal is necessary. The human may edit the in-app draft. Never copy the temporary file over the original before or after review.
4. **Prompt for UI review, then wait in this turn.** Keep all returned `reviewIds`. Send a short commentary such as “已提交到 DiffEditor，请在软件内审阅并确认保存；我会等待保存回执，无需再在聊天确认。” Run `wait <reviewId> [reviewId...]` with all IDs. Keep the task active until the command returns; do not send a final answer and leave a background process waiting. If the shell tool returns a session ID, continue on that same process, with each tool wait at most 60 seconds. Avoid frequent status polling and repeated reminders. Honor user interruption. The default overall deadline is 1800 seconds; use another bounded timeout only when appropriate and do not restart waits indefinitely.
5. **Read outcomes per file and retain unresolved rounds.** A save requires `status: saved` and a receipt for that target; `reason: saved` additionally requires every selected review to have targets and every target to meet that condition. Partial saves remain waiting for other files. `attention` and `timeout` are observations, not approval. A confirmed save, human UI rejection/return or deletion, or successful withdrawal of the AI's own unsaved, human-unedited proposal ends the round. Closure, timeout, conflict, error, connection loss, and restart do not. `withdrawn` means AI withdrawal, not human rejection or saving; report it separately. Fully saved AI proposals and successfully withdrawn proposals automatically close into the top of the closed list, newest completion first. Drafts and history remain available; the human may reopen them to view/copy, and retries must not close manually reopened history again. A closed lifecycle alone still does not prove saving; check the receipt or withdrawn status. A deleted comparison is a tombstone and must not be restored automatically. Saved receipts remain valid after closure or deletion. After a bounded wait expires, report pending states and finish the turn without treating timeout as an ended round or seeking a second chat confirmation.
6. **Respect save control and protect human edits from withdrawal.** AI proposal buttons are 退回 for the original and 通过 for the new draft; only the human's real final UI confirmation may save, backing up an existing target first. Never automate save, human return, close, or delete actions, use private IPC for them, or overwrite the user's saved result. Chat agreement does not replace UI saving. The supported `withdraw <reviewId> --request-id <original-submit-requestId>` command may retract only your own unsaved proposal that has never been edited by the human on either side. An edit followed by undo still counts. The app freezes the editors briefly, flushes pending edits and checks the durable revisions before withdrawal. `WITHDRAW_HAS_HUMAN_EDITS` means leave that round and its drafts intact, report the refusal, and wait for the user's UI decision; do not bypass it, obtain another baseline, or automatically resubmit. If the renderer is unavailable or preflight fails/times out, preserve the round and report the error. The current CLI always requests the unedited-only policy, so an older running app must reject it rather than silently use a permissive withdrawal policy; never remove this guard or fall back to an older CLI. Use your retained original request ID, not another agent's credentials. A successful withdrawal keeps drafts/history, ends the round without writing the target and returns a receipt; repetition cannot revoke a saved result. If authorized work remains, finish it in a temporary draft, capture a fresh actual-disk baseline and submit once at the next approval point. Old baselines remain expired. Do not repeatedly withdraw/resubmit intermediate edits. Human return/deletion still does not authorize automatic resubmission without new user-requested scope.

## Invocation and schemas

Read [references/cli.md](references/cli.md) for exact commands, JSON examples, and status handling. For deterministic invocation without shell content interpolation, use [scripts/invoke_diffeditor.py](scripts/invoke_diffeditor.py):

```text
python <skill-dir>/scripts/invoke_diffeditor.py baseline <absolute-target.tex>
python <skill-dir>/scripts/invoke_diffeditor.py submit --file <absolute-inbox-candidate.json>
python <skill-dir>/scripts/invoke_diffeditor.py wait <reviewId> [reviewId...] --timeout 1800
python <skill-dir>/scripts/invoke_diffeditor.py status <reviewId>
python <skill-dir>/scripts/invoke_diffeditor.py withdraw <reviewId> --request-id <original-submit-requestId>
```

The helper discovers a bundled installation, `DIFFEDITOR_HOME`, or `D:\Project\diffEditor`. `DIFFEDITOR_HOME` is the directory containing `diffeditor.cmd`. It invokes Node/Electron using an argument array and forwards stdin, UTF-8 JSON output, and the exit code. It keeps the caller's working directory. Packaged installations run without a separate system Node installation. Use the argument-array examples in the reference when calling it from an AI workflow; no GUI automation is needed for baseline, submit, wait, status, or withdrawal.

## Retries and conflicts

- A duplicate submission returns the existing review IDs, including closed or deleted comparisons. Query their status; the same request ID is only for the identical payload. Do not regenerate a candidate, replace a comparison with a new ID, or overwrite a user's in-app edits. `REVIEW_IN_PROGRESS` means inspect/wait on those existing IDs, or explicitly withdraw your own unsaved proposal if it needs retracting; never bypass the block with a new request ID, baseline, comparison, or path alias. `BASELINE_EXPIRED` means a prior round consumed the old snapshot: inspect its review IDs and confirm that round has ended and a new revision is authorized before obtaining a fresh baseline. Neither error authorizes automatic resubmission.
- After a timeout or truncated response, the operation may have reached the app. Query known review IDs (or inspect `status` when IDs were not returned) before deciding whether an exact retry is necessary. Retry only the identical payload with the same request ID. Stop when the outcome remains uncertain; never claim success from application launch.
- If a wait connection fails, report the failure, inspect the same review IDs with `status` when available, and resume `wait` on those IDs only within the remaining overall deadline. Do not resubmit, change a baseline, or claim completion. If the installed/running app does not support `wait`, ask the user to exit the old version from its tray menu and start the updated version; do not kill or quit their app automatically. Do not silently replace this workflow with a final answer asking the user to confirm later in chat.
- On conflict or error, preserve the pending draft and both versions. Explain the state; do not update the baseline, force-save, or overwrite the target. The round remains unresolved until a human save/return/deletion or successful withdrawal through the public command. Uncertain save outcomes cannot be withdrawn; inspect the failure and obtain human recovery instead. A request for further work does not itself clear the round.
- Preserve inbox artifacts and remaining in-app drafts after rejection/return, conflict, or error; none authorizes AI deletion or resubmission. A deleted comparison's draft may no longer exist; report its tombstone without restoring it. After a round ends, follow the distinct human-return and AI-withdrawal paths above; a later authorized revision starts from the current file with a fresh baseline, never an automatically replayed old draft.
- If DiffEditor is missing or fails to start during review, report the problem and leave those formal files untouched. Do not substitute a direct write for a required review. First-draft creation does not require the app. Do not change hooks, configuration, or install globally as a side effect.
