# DiffEditor

Use this workflow automatically for authorized creation and editing of material intended for the user to read, such as their papers, knowledge explanations, study notes, and discussion records. Reports and documentation qualify when they are reading material for the user. Adding text, proofreading, formatting, and restructuring count as edits. Decide by the material's intended use, not its extension, repository location, or edit size. Also use it when the user explicitly requests DiffEditor for another text review. Before writing, establish which files and claims the user authorized changing. Propose out-of-scope issues in chat without changing them. Preserve existing todo items and their states.

## Scope and execution boundary

- **Default exclusions:** Code, configuration, agent instruction files, and the agent's internal execution records (task checklists, progress logs, execution plans, and intermediate working notes) do not require DiffEditor unless the user explicitly requests review of them. Read-only analysis and ordinary chat replies also do not require it. A Markdown progress log used only to track the agent's work is not the user's knowledge note; a document prepared for the user to read is not exempt merely because it is named a log or checklist.
- **Tools do not change the scope:** For material requiring review, direct edits, patches, Python/PowerShell/shell scripts, batch jobs, other skills, delegated agents, and external tools obey the same boundary. A script must write to a separate temporary draft, then submit that draft for comparison with the original as described below. It must not write the review-gated original. Pass this boundary explicitly to delegated agents and check their results. Available write access is not permission to bypass review.
- A one-time user instruction to skip diff and write directly applies only to the specified files and changes in that authorized round. Do not carry it into later revisions, other files, or another task. Ordinary chat approval such as "可以", "保存吧", or "继续" does not waive review. Never rewrite the user's saved result after receiving a receipt.
- DiffEditor handles plain text, including `.tex`, `.md`, `.bib`, `.txt`, and textual HTML. For unsupported formats or document services, explain the limitation and obtain the user's choice of a reviewable route before modifying the formal document. Do not treat lack of support as permission for a direct write or pretend a text receipt proves that a different document was saved.

## Choose the path per file

Apply these paths only to material within the review scope above; editing excluded code or internal progress records does not become review-gated after its first write.

- **First draft of a new document:** When the user authorizes creating a document, write its first content directly without a diff review or `baseline` / `submit` / `wait`, unless the user explicitly requests review of that first draft. Prefer creating the file once with its complete first draft using exclusive creation (`open(path, "xb")` in Python; `FileMode.CreateNew` in .NET). If you already created an empty placeholder in this task, verify that it is that same file and still empty before filling it. Read back the result before reporting creation complete; no DiffEditor receipt is needed for this path.
- **Revisions:** Once the first draft has been written, subsequent changes require the review workflow below, even within the same task. Existing files, including empty files not created by you in this task, also use review. Never clear, delete, or recreate an existing document to qualify as a first draft; an existing pending proposal must remain in its review workflow.

For tasks mixing new documents and revisions, choose independently for each file and report direct creations separately from review save receipts.

## Review workflow

1. **Capture immutable baselines before generating candidate text.** Run `baseline` for every target requiring review (including a new file when its first draft explicitly requires review). Read the returned text, encoding, existence flag, hash, and baseline ID. Preserve the JSON receipt using exclusive creation in a unique workflow directory under the app inbox. Never replace a baseline with a fresh one to bypass a conflict or manufacture a clean comparison.
2. **Write the candidate only in the app draft area.** The inbox is `%LOCALAPPDATA%\DiffEditor\inbox`; when `DIFFEDITOR_DATA_DIR` is set, use that directory's `inbox`. Create a unique workflow subdirectory there and preserve the baseline receipt. If a script will write the document, first create a distinct temporary text file there, such as `proposed.md` or `proposed.tex`; initialize it from the captured baseline when editing existing text. Set the script's output (and its input for in-place transformations) to this temporary path. Run the script against the temporary file, then read back and check the full resulting text. The temporary draft must be an independent file, not a link or alias to the original. Do not create or overwrite the review-gated original, and do not place temporary candidate files in its directory.
3. **Submit the original and temporary draft for comparison.** Serialize the original file's baseline ID and the complete proposed text into UTF-8 `candidate.json` in the same workflow directory. For script-generated text, read the text from the temporary file while preserving its newlines. The CLI takes baseline IDs and text, not a pair of file-path arguments: the original baseline appears as the original, the temporary file's contents as the new draft, and the original path remains the save target. Do not capture a baseline of the temporary file instead. Run `submit --file <absolute-candidate.json>` or feed the JSON bytes through `submit --stdin`. Never interpolate document text into a shell command, command-line flag, or here-string. Generate JSON with a real serializer, preserving quotes, backslashes, Unicode, and newlines. Assign one unique `requestId` to this proposal and retain it for an exact retry. DiffEditor stores the submitted editable draft in its own data directory; do not copy the temporary file over the original before or after review.
4. **Prompt for UI review, then wait in this turn.** Keep the returned `reviewIds`. Send a short commentary such as “已提交到 DiffEditor，请在软件内审阅并确认保存；我会等待保存回执，无需再在聊天确认。” Then run `wait <reviewId> [reviewId...]` with all submitted IDs. Keep the current task active until the command returns; do not send a final answer and leave a background process waiting. This is not an automatic wake-up mechanism for a finished chat. If the shell tool returns a session ID, continue waiting on that same process, with each tool wait at most 60 seconds. Avoid frequent `status` polling and repeated reminders. Stop if the user interrupts. The default overall wait is 1800 seconds; choose another bounded `--timeout` only when appropriate, and do not restart waits indefinitely when that deadline expires.
5. **Read the wait result per file.** `reason: saved` requires every selected review to have at least one target and every target to have `status: saved` plus a receipt. Partial saves remain waiting while the other files await review. `attention` reports conflict, error, rejection, or an unsaved closed/deleted comparison; explain each file's actual state without resubmitting or rewriting it. `timeout` reports current states, not success. Inspect `lifecycle` separately: `closed` comparisons may be reopened by the human in the UI; `deleted` comparisons must not be recreated without a new user request. A saved receipt remains valid when its comparison is later closed or deleted. A successful submit, duplicate response, or exit code 0 alone proves neither approval nor saving. Report saved, pending, and failed targets individually. After a wait timeout, report what remains pending and finish; do not ask for a second chat confirmation.
6. **Respect final UI control.** For targets undergoing review, only the user's real UI confirmation may write formal files. Never automate final clicks, call private IPC, write such targets directly, or invent approve/save/force/close/delete commands. Chat permission such as “可以”“保存吧” is not the UI confirmation. The UI save backs up an existing target before replacing it; a new target has no old file to back up. Report a reviewed target as saved only when its `status` is `saved` and its `receipt` is present. A receipt proves the UI saved the recorded side and bytes; the human may have saved the original or manually edited text, so do not claim that the AI proposal was accepted in full.

## Invocation and schemas

Read [references/cli.md](references/cli.md) for exact commands, JSON examples, and status handling. For deterministic invocation without shell content interpolation, use [scripts/invoke_diffeditor.py](scripts/invoke_diffeditor.py):

```text
python <skill-dir>/scripts/invoke_diffeditor.py baseline <absolute-target.tex>
python <skill-dir>/scripts/invoke_diffeditor.py submit --file <absolute-inbox-candidate.json>
python <skill-dir>/scripts/invoke_diffeditor.py wait <reviewId> [reviewId...] --timeout 1800
python <skill-dir>/scripts/invoke_diffeditor.py status <reviewId>
```

The helper discovers a bundled installation, `DIFFEDITOR_HOME`, or `D:\Project\diffEditor`. `DIFFEDITOR_HOME` is the directory containing `diffeditor.cmd`. It invokes Node/Electron using an argument array and forwards stdin, UTF-8 JSON output, and the exit code. It keeps the caller's working directory. Packaged installations run without a separate system Node installation. Use the argument-array examples in the reference when calling it from an AI workflow; no GUI automation is needed for baseline, submit, wait, or status.

## Retries and conflicts

- A duplicate submission returns the existing review IDs, including closed or deleted comparisons. Query their status; do not regenerate a different candidate with the same request ID, replace a deleted comparison with a new ID, or overwrite a user's in-app edits.
- After a timeout or truncated response, the operation may have reached the app. Query known review IDs (or inspect `status` when IDs were not returned) before deciding whether an exact retry is necessary. Retry only the identical payload with the same request ID. Stop when the outcome remains uncertain; never claim success from application launch.
- If a wait connection fails, report the failure, inspect the same review IDs with `status` when available, and resume `wait` on those IDs only within the remaining overall deadline. Do not resubmit, change a baseline, or claim completion. If the installed/running app does not support `wait`, ask the user to exit the old version from its tray menu and start the updated version; do not kill or quit their app automatically. Do not silently replace this workflow with a final answer asking the user to confirm later in chat.
- On conflict, preserve the pending draft and both versions. Explain the conflict; do not update the baseline, force-save, or overwrite the target. Let the user resolve it in the UI or explicitly request a new proposal from a new baseline.
- Preserve inbox artifacts and remaining in-app drafts on rejection, conflict, or error; those states are not authorization to delete or resubmit. A deleted comparison's draft may no longer exist; report its tombstone status without restoring it. A follow-up revision needs the user's requested scope and must preserve existing draft content until a new proposal is deliberately created.
- If DiffEditor is missing or fails to start during review, report the problem and leave those formal files untouched. Do not substitute a direct write for a required review. First-draft creation does not require the app. Do not change hooks, configuration, or install globally as a side effect.
